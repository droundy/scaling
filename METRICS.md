# Metrics: extra computed data with each cell

A benchmark's timing is one number about a cell (one candidate on one input).
Often the interesting question is about something else the candidate
produced: how many bytes a serializer wrote, how well its output compresses,
how much memory it peaked at. This plans a way to attach any such number to a
cell and show it in the tables from `Report::groups()`.

It builds on `Group` and `formatting` from the `flexible-tables` branch
(#17), and is stacked on it.

## Prior art

[rust_serialization_benchmark](https://github.com/djkoloski/rust_serialization_benchmark)
reports, per dataset, one table with a row per library and the columns
Serialize, Deserialize, Size, Zlib, Zstd and Zstd Time, and a second copy
with each cell as a percentage of the best in its column. Each library's
`bench()` calls `bench_size(name, library, buffer)` beside its timing code,
so the non-timing columns are derived from what the library produced. (How
the two sets of numbers are merged into the final tables is not checked
here.)

What carries over:

- the extra data is a function of what the benchmark produced, computed once
  and not timed;
- a table of one input with the time and the metrics across.

Not carried over: its percent-of-best view, which needs to know which way
is better for every metric.

## Concepts

A **metric** is a named number computed once per cell, after sampling, so it
cannot disturb the timing. It has a unit, which decides how it is printed.

Two kinds:

- **Derived**: a function of the benchmark's output (and optionally its
  pristine input). Size, compressed size, compression ratio, a correctness
  check.
- **Observed**: wraps one extra run of the candidate. Peak memory, allocation
  counts, single-shot elapsed time. Needed because some quantities are not
  in the output at all, and a candidate returning `()` has no output.

## Declaring derived metrics

The function **consumes** the output, so it needs no `Clone`, can reuse the
buffer, and can check it (decode and compare with the input). Because a
consumed output can feed only one function, one function per group
produces a *record* of metrics, rather than one function per metric:

```rust
#[scaling::bench(group = "serialize", baseline)]
fn json(m: &mut Mesh) -> Vec<u8> { serde_json::to_vec(m).unwrap() }

#[scaling::bench(group = "serialize")]
fn postcard(m: &mut Mesh) -> Vec<u8> { postcard::to_allocvec(m).unwrap() }

#[scaling::metrics(group = "serialize")]
fn sizes(out: Vec<u8>) -> scaling::Metrics {
    scaling::Metrics::new()
        .bytes("size", out.len())
        .bytes("zstd", zstd::encode_all(&out[..], 3).unwrap().len())
}

// with the pristine input as well
#[scaling::metrics(group = "serialize")]
fn per_vertex(mesh: &Mesh, out: Vec<u8>) -> scaling::Metrics { ... }
```

- Signatures: `fn(O) -> Metrics` or `fn(&I, O) -> Metrics`, where `O` is the
  candidate's return type and `I` its input. The argument count selects the
  form.
- `Metrics` is a builder: `.bytes`, `.count`, `.ratio`, `.percent`,
  `.seconds`, or `.value(name, v).unit(..)`. Names are given where the number
  is, so the unit sits beside it.
- A metric function pairs with candidates on `(group, output type)`, and on
  input type for the two-argument form: the way inputs already pair. A
  candidate with another output type shows `-`.
- Exactly one function per `(group, output type)`. A second one is a
  diagnostic from assembly, as for any other conflicting registration.
- Standalone benchmarks get an inline form, `#[bench(metrics = |out| ..)]`.
  It expands inside the shim, where `O` is known, so it needs no erasure
  and the output need not be `'static`. The group form pairs by `TypeId`, so
  it does need `O: 'static`.

## Declaring observed metrics

```rust
#[scaling::metrics(group = "serialize", observe)]
fn memory(run: &mut dyn FnMut()) -> scaling::Metrics {
    scaling::Metrics::new().bytes("peak", scaling::alloc::peak_during(run))
}
```

The harness hands in a closure that runs the candidate once. Ship
`scaling::alloc::CountingAlloc`, which a user opts into with
`#[global_allocator]` (a library cannot install one for them), plus built-in
`peak_bytes` and `allocations` observers.

## Runtime

1. `Candidate` gains `output_type` and a `run_once` shim,
   `fn(&mut ErasedInput) -> Box<dyn Any>`, generated by the macro, which
   knows `O`.
2. A `MetricsFn` registration carries its group, output and input types,
   whether it is observed, and an erased evaluator
   `fn(&ErasedInput, Box<dyn Any>) -> Metrics`.
3. `assemble::plan` pairs them, and warns about a function that matches no
   candidate and about duplicates.
4. When a cell finishes sampling, a final step clones a fresh input per
   candidate and runs it once. One run feeds the derived function. Each
   observed function gets its own run. It is single-shot, so it is meant for
   deterministic quantities, and the docs say so.
5. A panic in a metric function fails the run and names the function.

## Data model

```rust
pub struct Group { ..., pub metrics: Vec<MetricColumn> }
pub struct MetricColumn {
    pub name: String,
    pub unit: Unit,
    /// Same shape as `Group::measurements`: values[candidate][input].
    pub values: Vec<Vec<Option<f64>>>,
}
```

A dense layer parallel to `measurements`. The column set is the union of the
names across candidates, in first-seen order, so a candidate that produces
no such metric gets `None`. Also `Report::metric(group, candidate, name)`, since
scripts reach results by name.

## Tables

Two layouts, chosen by shape.

**Stacked**, for a group with several inputs and one or two metrics: the
candidates-down, inputs-across grid a group without metrics has, with each
candidate's metrics on the lines beneath its time, named in the margin.

```
serialize (Mesh)  baseline: json
candidate              mesh              log
json         81.2ns ± 0.8ns   40.0ns ± 0.4ns
  size              1.90MiB          2.00KiB
postcard    -61.08% ± 0.15%    -25.0% ± 0.3%
  size        737KiB (-62%)      512B (-75%)
```

**A table to an input**, for one input or more than two metrics: candidates
down, the time and then each metric across.

```
serialize@mesh (Mesh)  baseline: json
candidate              time           size         ratio  ...
json         81.2ns ± 0.8ns        1.90MiB         0.310
postcard    -61.08% ± 0.15%  737KiB (-62%)  0.520 (+68%)
```

- Metrics are exact, so their delta needs no significance test: baseline row
  absolute, other rows `value (Δ%)`. Time keeps its convention.
- Values format by unit: `bytes` picks KiB or MiB, `ratio` three significant
  digits, `custom` a given suffix.
- A stack that is too wide for the page becomes tables to an input. A table
  to an input that is too wide is turned on its side, and if it is too wide
  either way it becomes one line per cell, with the metrics as more columns.
- There is no notion of which direction is better, so nothing marks a best
  value.

## Phases

1. Data model and formatting, from hand-built `Group`s with expect-tests. No
   runtime change.
2. Hand-built API for `add_input_group`: `.metrics(|out: Vec<u8>| ..)`. The
   group needs its output type as a parameter.
3. Registry and macros: `#[metrics]`, the candidate shim, assembly pairing
   and diagnostics.
4. Observers: `CountingAlloc`, `peak_bytes`, `allocations`.
5. Options: a `Config` switch to skip metrics, a runner flag
   to select them.

## Open questions

- **Per-candidate exceptions.** A function cannot say "not for this
  candidate"; `None` covers unsupported metrics but not a different unit.
- **Time budget.** Should the metric step count against `max_time`? A slow
  one (zstd) would eat into it. Leaning towards running it outside the
  budget and reporting how long it took.
- **Scaling benchmarks.** `bench_scaling` has no single cell to attach to.
  Leave out of the first version.
- **Several inputs.** One sub-table per input matches the prior art; one
  table per metric is easier to scan across inputs. Start with per-input,
  make it a `Config` option.
- **Derive.** A `#[derive(Metrics)]` struct could replace the builder once
  the shape settles.
